## 0. 核实结论（重要：修正两份文档的过时表述）

本裁决基于代码逐行核实，而非仅依赖 `PROGRESS.md` / `outputs/玩法差异对比.md` 的结论。核实后确认：**两份文档的多数"缺陷/简化"表述已与当前代码脱节（STALE）**，直接关系到裁决口径，先予纠正。

### 0.1 缺陷 #1「两套战斗解算不一致」—— 基础公式已统一，残余的是"交互层"而非"公式层"

`PROGRESS.md` 称 `ActionDungeon.battle()`「前缀未接入、忽略减伤、不耗耐久」。实测代码**已非如此**：

| 维度 | 交互式 `ActionCombat`（主页/地图/地牢） | 自动式 `ActionDungeon.battle()`（事件） |
|---|---|---|
| 前缀修正 | `ActionCombat.applyPrefix` (`ActionCombat.ts:86,171`) | 同 `ActionCombat.applyPrefix` (`ActionDungeon.ts:354`) |
| 玩家攻击 | `calcPlayerAtk`（含技能加成/装备倍率/阵营） | 同 `calcPlayerAtk` × 前缀 (`ActionDungeon.ts:373`) |
| 装备减伤 | `calcDamageReduce` (`ActionCombat.ts:256`) | 同 `calcDamageReduce` (`ActionDungeon.ts:379`) |
| 武器耐久 | `decayWeapon` (`ActionCombat.ts:300`) | 同 `decayWeapon` (`ActionDungeon.ts:374`) |
| 防具耐久 | `decayArmor` (`ActionCombat.ts:264`) | 同 `decayArmor` (`ActionDungeon.ts:382`) |
| 命中率 | 射程比对 0.9/0.6 (`ActionCombat.ts:98`) | 同 (`ActionDungeon.ts:365`) |

> 结论：**基础战斗公式（前缀/攻击/减伤/耐久）已完全共用同一套函数**，不存在"难度与后果不同"的公式级偏差。`ActionDungeon.battle()` 注释亦自陈"公式与 ActionCombat 完全一致"。

**真正的残余不一致在"交互层"**：交互式战斗支持 5 技能独立效果+冷却、防御/敏捷姿态、逃跑、战斗内道具；而事件战斗走 `ActionDungeon.battle()` 自动解算，**没有技能、没有逃跑、没有玩家抉择**。详见第 1 节。

### 0.2 缺陷 #2「地图怪数量不递减」—— 在交互路径上真实存在

`PROGRESS.md` 称 `ActionMap.hunt` 过滤 `amount>0` 后直接战斗未扣减。实测：
- `ActionMap.hunt`（`ActionMap.ts:105-120`）**确实已含胜利后扣减逻辑**（`entry.amount -= 1`），但——**该方法已是死代码，全工程无任何调用方**（grep `ActionMap.instance.hunt` 无结果）。
- 真正的地图狩猎 UI 路径是 `OutdoorPage.ts:665-669`：`probeHunt` → `battlePanel.startBattle(mstId)`（**交互式**），胜利后经 `MainScene.onBattleEnd`（`MainScene.ts:995`）**只 `UI_REFRESH`，不扣减 `mst.amount`**。

> 结论：**缺陷 #2 在"交互式地图狩猎"这条真实路径上确实存在**。采集 `gather` 会 `amount-1`（`ActionMap.ts:63`）且资源显示"枯竭"（`OutdoorPage.ts:388-430`），而狩猎不递减，二者不自洽。这是需要修复的真缺陷。

## 1. 战斗解算一致性决策

### 1.1 决策问题（重述为准确口径）
> 事件遭遇战是否应统一到 `ActionCombat` 的**完整交互公式**？

基础公式已统一（见 0.1），故问题精确化为：**事件战斗目前是"无玩家抉择/无逃跑"的自动解算，是否应改为与地图/地牢一致的交互式战斗（玩家可选技能/防御/敏捷/道具/逃跑）？**

### 1.2 推荐方案

**推荐：采用「Option A —— 事件战斗改走交互式 BattlePanel」，与地图狩猎 `OutdoorPage.ts:665-669` 完全对齐。** 即：事件中触发 `mst` 时，不再调用 `ActionDungeon.battle()` 自动解算，而是经事件总线向 UI 请求打开 `BattlePanel.startBattle(mstId)`；事件奖励（`get`/`chanceGet`/`skill`）按现状在触发时先行结算，战斗胜负只影响玩家存亡，不重复发放奖励。

**理由**：
- 设计正确性：同一只怪在"地图遇之"可逃跑/用技能，在"事件遇之"却被强制无逃跑自动战，违反"同一怪=同一规则"原则，造成**后果层面的不公平**（事件易成必死陷阱）。
- 工程可行性：地牢战斗 `DungeonPage.ts:90-94` 已是"抽到怪→`BattlePanel.startBattle`"的同款模式，事件套用零新增架构，仅需在 `ActionEvent` 与 UI 间加一个"请求战斗"的事件总线信号（参照 `DungeonPage` 做法）。
- 公式零改动：底层 `applyPrefix/calcPlayerAtk/calcDamageReduce/decay*` 全部复用，不存在重写公式的风险。

**代价**：
- 工作量：低-中。需 (a) `ActionEvent.trigger` 在 `onDone` 内若有 `data.mst` 则改发"请求战斗"信号而非直接 `battle()`；(b) `EventPage`/UI 订阅该信号并调用 `BattlePanel.startBattle`，战斗结束 `onEnd` 仅 `UI_REFRESH`；(c) 因事件 `onDone` 为异步进度回调，需确认"奖励先发、再开战"的时序不破坏现有存档原子性（奖励本就在 `onDone` 内先于 `battle` 发放，拆分后逻辑等价）。
- 平衡风险：低。交互式战斗通常**更易**取胜（有防御/敏捷/逃跑），事件难度可能整体下降；建议 QA 抽取 3-5 个含 `mst` 的事件回归，确认难度曲线不崩。

**不统一的后果（若维持现状）**：
- 公平性缺陷：玩家在事件中遭遇强怪时**无任何逃生手段**，一旦属性不足即必死，且死亡惩罚（转生/重生）沉重 → 玩家体感"被脚本谋杀"。
- 难度不一致：QA 若在"主页战斗"调平衡，"事件同怪"会表现迥异，导致平衡基准失真。
- 门控风险：第 ⑥ 阶段 full 门控要求"设计一致性"，此不一致会被记为未收口项。

**降级方案（Option B，仅作安全下限）**：若 Option A 因事件流时序风险暂缓，则对 `ActionDungeon.battle()` 增加**安全撤退**：当自动解算预测玩家 HP 将跌破阈值（如 <20% 或致死）时，按"逃跑失败但保命"处理（不扣致死、仅消耗时间/小伤），杜绝强制必死。代价极低，但**仍无技能/抉择**，属次优。

> 裁决结论：**P0 以 Option B 作为不阻塞交付的安全下限；目标态为 Option A，建议在 P1 完成统一**。若工期允许，直接上 Option A。

### 1.3 顺带裁决：主页"战斗"调试入口
`MainScene.ts:981` 的"战斗"页列出全部 99 怪可直选开战（`PROGRESS.md` 表 `#23` 已标"非原版调试入口"）。
- **决策**：Demo 期保留为便捷入口；**发布/上架前须 gate 在调试开关后**（或改为"仅挑战已解锁层级"），否则可越级挑战终盘 Boss 破坏平衡，且此入口**不计入**地图怪递减逻辑（无限刷），不能作为平衡参考基准。

## 2. 地图怪递减决策

### 2.1 现状（见 0.2）
真实路径 `OutdoorPage → probeHunt → BattlePanel` 胜利后**不扣减**地点 `mst.amount`；而采集 `gather` 会 `amount-1` 并显示"枯竭"。设计哲学不自洽：**资源会枯竭，怪物却无限刷**。

### 2.2 推荐方案

**推荐：接入 `mst.amount` 扣减，与采集 `gather` 的枯竭模型严格一致。**

- **扣减时机**：仅在**胜利**时 `-1`；逃跑/阵亡不扣（逃跑=怪仍在，符合直觉；阵亡已在死亡流程处理）。
- **扣减位置**：把 `ActionMap.hunt`（`ActionMap.ts:112-118`）里已写好的扣减片段**抽成独立方法**（如 `ActionMap.onHuntWin(placeId, mstId)`），由 `OutdoorPage` 的胜利回调调用；并 `emit('place_change', placeId)` 刷新"有怪/枯竭"提示（`OutdoorPage.ts:117,595-602` 已读取 `amount` 展示，扣减后 UI 自然显示递减/枯竭）。
- **删死代码**：`ActionMap.hunt` 自动战斗路径无调用方，扣减逻辑迁移后**删除该方法**，避免"两条狩猎路径行为不一"的隐患。
- **边界兼容**：`mst.amount` 为 `undefined`（旧档/未配置上限的地点）时视为"无限刷新、不递减"，保持向后兼容，不强制所有地点都枯竭。

### 2.3 与采集/拾荒的枯竭逻辑一致性
- 采集 `gather`：永久递减、不自然恢复（`ActionMap.ts:63`）→ 狩猎采用**同样的永久递减、不恢复**模型，二者哲学统一。
- 拾荒 `scavenge`：随机散落物、**不递减池子**（开放式），属不同模型，不强行对齐。
- 地牢战斗：按层抽怪、不递减（grind 设计），与地图地点枯竭模型分离，**不要求**地牢也递减。

**代价**：低-中（约 1 处 action 方法抽离 + 1 处 UI 回调接线）。**风险**：低（纯减法计数，不影响战斗公式）。
**不做的后果**：地图点可无限刷怪 → 怪物掉落物（材料/金币等价物）无限产出 → 经济与制造链失衡；与"资源枯竭"叙事矛盾，被记为设计不自洽。

## 5. 工程实现注意点（Handoff 给主理人 / 工程）

1. **先校正文档再动手**：`PROGRESS.md` 缺陷 #1/#2 与 `玩法差异对比.md` 多处表述已过时。工程开工前请先按本裁决 §0 更新文档，避免误删/误改已实现的逻辑（尤其 `ActionCombat`/`ActionDungeon.battle` 的共用公式——**切勿"重写"已统一的公式**）。
2. **事件战斗改交互式（D1）的时序陷阱**：`ActionEvent.trigger` 的奖励结算在 `ActionExecutor` 的 `onDone` 异步回调内；若改为"先发奖励→请求战斗"，需保证战斗打开前奖励已落档，且战斗结束 `onEnd` **不再二次发放**。建议复用 `DungeonPage` 的"抽怪→`BattlePanel.startBattle`→`onEnd` 仅刷新"模式，最稳。
3. **地图怪递减（D2）接线点**：递减逻辑应从 `ActionMap.hunt` 抽离后，由 `OutdoorPage` 的胜利回调（`battlePanel.onEnd` 本地覆盖，或经 `MainScene.onBattleEnd` 携带 placeId）调用；注意当前 `onBattleEnd` 无 placeId 上下文，需补传战斗来源（placeId+mstId）。
4. **删 `ActionMap.hunt` 死代码**：确认无任何调用方后删除；若担心回退，保留方法但标注 `@deprecated`，不要让其与交互路径并存两套递减逻辑。
5. **平衡回归**：D1 若上 Option A（交互式更"易"），事件整体难度或下降，建议 QA 用原版数值抽 3-5 个事件做难度对照；D2 递减后，原依赖"无限刷某地图怪"的速刷流被砍，需确认是否有合法替代farm点。
6. **门控对照**：第 ⑥ 阶段 full 门控以"设计一致性"为准。本裁决判定——**公式一致性已达标（✅）**；**仅 D1、D2 为未收口项**，需在 full 门控前落地其一（Option B 即可过门控，Option A 为最终态）。
