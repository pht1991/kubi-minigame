## 〇、结论速览（主理人先看这里）

**结论：首版建议「带轻量音效（SFX 优先），BGM 可选 / 推迟到 P2」。**

- 当前版本**确认无声**：代码层（`assets/scripts/`，72 个 TS 文件）没有任何 `AudioManager`、`wx.createInnerAudioContext`、`AudioClip` 播放逻辑。
- 仅存两處"伪音频"痕迹，均**未接通**：
  1. `data_item.ts` 中部分物品带 `sound:'scroll'` 字段（如回城卷轴），是移植自原版 KuBi 的死数据，无任何读取/播放代码。
  2. `GameManager.settings.volume` 与 `MenuPage` 的音量 +/- 滑块 UI 已存在，但**没有任何引擎消费这个数值**。
- 双端（微信 + 网页）都缺音频实现；原版 KuBi 的 `res/` 音效资源也**未导入本工程**（工程中 0 个 `.mp3/.ogg/.wav/.m4a/.aac` 文件）。

**推荐理由一句话**：文字游戏的"手感"高度依赖点击/战斗/结算的即时声反馈，而本作架构（EventBus 事件 + 单例管理 + volume 设置 + SaveManager 双端范式）已为音频铺好接入点，SFX 工作量小、包体占用极低（百 KB 级），收益/成本比高，应在首版补齐。

> 备选：若首版工期/资源极度紧张，可接受「静音首版」+ 下方 P2 路线图兜底（见 §6）。但鉴于接入成本极低，**不推荐静音首版**。

## 一、现状确认（证据链）

| 检查项 | 结果 | 证据 |
|--------|------|------|
| 是否实现 `AudioManager` / `SoundManager` | ❌ 否 | `assets/scripts/core/` 仅有 `SaveManager / EventBus / GameManager / TimeSystem / GridNavigator / ActionExecutor / PerfTier`，无音频管理类 |
| 是否调用 `wx.createInnerAudioContext` | ❌ 否 | 全仓（含 build 产物外）零命中 |
| 是否使用 `AudioClip` / Cocos 音频组件 | ❌ 否 | 无 AudioSource 节点、无 AudioClip 资源引用 |
| 是否有音频资源文件 | ❌ 否 | `find` 全工程 0 个音频文件（已排除 node_modules/library） |
| `sound` 数据字段是否被读取 | ❌ 否 | `data_item.ts` 的 `sound:'scroll'` 为死数据，无 `item.sound` 读取逻辑 |
| `volume` 设置是否生效 | ❌ 否 | `GameManager.settings.volume` 仅被 `MenuPage` 滑块改写，无任何播放增益消费 |
| PROGRESS.md 是否提及音频 | ❌ 否 | 文档全文无 audio/sound 字眼，仅 §五提"无声"隐含风险未列 |

**结论**：首版若直接上线，**玩家听不到任何声音**。移植方案中规划的 `AudioManager → wx.createInnerAudioContext`（架构图 4.2）尚未落地，是方案 A 的遗留缺口。

## 二、为什么文字游戏仍该带音效（价值 vs 成本）

### 2.1 音频对体验/留存的价值
- **即时操作反馈**：文字 UI 缺乏动画张力，点击声、确认声是"我按到了"的最低成本确认，移动端尤其重要（无键盘哒哒声）。
- **战斗爽感**：攻击/受击/胜利/死亡音效是放置-战斗循环的情绪锚点，文字描述无法替代。
- **状态变化的"警示"**：死亡、偷家（ROBBER_RAID）、季节更替等需要"被听见"，玩家常后台挂机，声音是比视觉更可靠的通知。
- **小游戏生态偏好**：微信小游戏榜单产品普遍有声反馈，静音首版在"手感"评分上吃亏，影响留存与口碑。

### 2.2 成本（可控且低）
- **工作量**：AudioManager 单例 + EventBus 订阅 + 资源导入 ≈ 1–2 人日，远低于其它系统。
- **包体**：短 SFX（mp3 64–96kbps、单声道）单个 5–25KB，全套 30–50 个约 200–500KB，仅占 4MB 主包的 5–12%；可进一步放入分包（不占主包）。
- **资源获取**：原版 KuBi `res/` 已含音效，可直接复用/重采样；亦可从免费音效库（如 Kenney、freesound CC0）补齐，无版权风险。
- **技术风险**：架构已就绪（见 §5），几乎无新坑。

### 2.3 决策矩阵
| 维度 | 带 SFX | 静音首版 |
|------|:---:|:---:|
| 玩家手感 | ★★★★☆ | ★☆☆☆☆ |
| 留存增益 | 中高 | 无 |
| 包体占用 | +0.2–0.5MB | 0 |
| 工作量 | 1–2 人日 | 0 |
| 上线风险 | 低 | 低 |
| **推荐** | **推荐** | 不推荐（仅兜底） |

## 三、音频事件清单（映射现有 GameEvents）

优先复用 `EventBus.ts`（`GameEvents`）已定义的事件，避免新增耦合。事件清单分三类：

### 3.1 操作/UI 反馈音（点击即响，最高优先）
| 音效 ID | 触发点 | 现有钩子 |
|---------|--------|----------|
| `sfx_click` | 任意按钮/格子点击 | UIButton / GridCell 点击 |
| `sfx_confirm` | 确认类弹窗（制造/装备确认） | ResultModal / ModalPanel |
| `sfx_cancel` | 取消/关闭弹窗 | ModalPanel 关闭 |
| `sfx_error` | 操作失败/资源不足 | Action 返回失败 |
| `sfx_scroll` | 使用卷轴类物品 | `item.sound === 'scroll'`（**已埋点，待接通**） |

### 3.2 系统/状态变化音（订阅 EventBus 自动触发）
| 音效 ID | 触发事件 | 说明 |
|---------|----------|------|
| `sfx_item` | `ITEM_CHANGE` | 获得/失去物品 |
| `sfx_equip` | `EQUIP_CHANGE` | 装备/卸下 |
| `sfx_build` | `BUILDING_CHANGE` | 建造/升级完成 |
| `sfx_science` | `SCIENCE_UNLOCK` | 科技解锁 |
| `sfx_skill` | `SKILL_CHANGE` | 技能升级 |
| `sfx_event` | `EVENT_TRIGGER` | 随机事件触发 |
| `sfx_newday` | `NEW_DAY` | 新的一天（晨钟感） |
| `sfx_season` | `SEASON_CHANGE` | 季节更替 |
| `sfx_harvest` | `HARVEST_READY` | 采集/收获产出 |
| `sfx_robber` | `ROBBER_RAID` | 盗贼偷家警报（高优先警示） |
| `sfx_reincarnate` | （转生 Action） | 轮回 |

### 3.3 战斗音（情绪核心）
| 音效 ID | 触发事件 | 说明 |
|---------|----------|------|
| `sfx_battle_start` | `BATTLE_START` | 进入战斗 |
| `sfx_attack` | 战斗每回合攻击 | ActionCombat 回合 |
| `sfx_hit` | 受击/怪物受击 | 伤害结算 |
| `sfx_win` | `BATTLE_END`（胜利） | 胜利 |
| `sfx_lose` | `BATTLE_END`（失败）/ `PLAYER_DEATH` | 战败/死亡 |

### 3.4 BGM（可选，P2 接入，首版可不做）
- `bgm_ambient`：城镇/日常循环（低音量环境垫底）
- `bgm_dungeon`：地牢探索
- `bgm_battle`：战斗时叠层/切换
- `bgm_boss`：魔王战

> **首版范围建议**：3.1 + 3.2 + 3.3 全做（约 15–20 个 SFX，0.2–0.4MB）；3.4 BGM 视资源与工期，宁可推迟也不占位。

## 四、双端实现策略

核心思路：**统一 `AudioManager` 抽象，内部按平台分流**，仿照现有 `SaveManager` 的 `typeof wx !== 'undefined'` 检测范式（见 `SaveManager.ts:33`）。业务层只调用 `AudioManager.instance.play('sfx_click')`，不感知平台。

### 4.1 平台检测
```ts
const isWeChat = typeof wx !== 'undefined' && typeof wx.createInnerAudioContext === 'function';
```

### 4.2 微信端：wx.createInnerAudioContext
- 每个 SFX 用 `wx.createInnerAudioContext()` 创建实例，`src` 指向包内相对路径（如 `audio/sfx_click.mp3`）或远程 CDN URL。
- **复用而非频繁 new**：短音效在 `init()` 时预创建一次缓存（注意 iOS 对并发实例数有限制，建议 SFX 池 ≤ 16 个实例，必要时串行排队）。
- `obeyMuteSwitch`：建议设为 `false`，避免用户物理静音键误关游戏音；音量统一由 `settings.volume` 增益控制。
- **自动播放限制**：微信需用户首次交互后才能播放。在 `MainScene` 首次 `touchstart` 后初始化音频上下文/解锁，避免首音丢失。
- 远程音频需在小游戏后台配置 `downloadFile` 合法域名（若走 CDN 分包）。

### 4.3 网页端：Web Audio API（优先）或 HTMLAudioElement（兜底）
- 优先 **Web Audio API**：用 `AudioContext` + `GainNode` 做全局音量（直接吃 `settings.volume`），支持淡入淡出、复用 `AudioBuffer`，体验最佳。
- 兜底 **HTMLAudioElement**：实现更简单，但全局音量控制需逐实例 `audio.volume`，且无法淡入淡出。`<audio>` 元素放在 `index.html` 或由 `AudioManager` 动态创建。
- 网页端无 4MB 限制（gh-pages 部署），但首屏需控制并发加载，建议 SFX 懒加载 + BGM 首屏后才拉取。

### 4.4 统一接口（AudioManager 契约）
```ts
class AudioManager {
  init(): void;                       // 平台分流 + 预创建 + 解锁
  play(soundId: string): void;        // 播放 SFX（自动按 volume 增益）
  playBGM(id: string): void;          // 播放/切换 BGM（循环）
  stopBGM(): void;
  setVolume(v: number): void;         // 同步 settings.volume
  setMuted(m: boolean): void;
}
```

## 五、接入点建议（与现有纯代码架构对齐）

1. **新增 `assets/scripts/core/AudioManager.ts`**：单例，仿 `SaveManager` 双端 fallback 结构。
2. **`MainScene` 初始化**：在 `onLoad`/`start` 中调用 `AudioManager.instance.init()`，并监听首个触摸事件以解锁微信音频。
3. **订阅 EventBus（自动化音效）**：在 `init()` 中订阅 §3.2/3.3 的 `GameEvents`（如 `BATTLE_START`→`sfx_battle_start`、`NEW_DAY`→`sfx_newday`、`ROBBER_RAID`→`sfx_robber`）。一处订阅，全游戏生效，零侵入业务逻辑。
4. **细粒度埋点（可选）**：在 `UIButton`/`GridCell` 点击、`ResultModal` 确认等具体位置直接调用 `AudioManager.instance.play(...)`，用于 §3.1 这种"非事件驱动"的反馈音。
5. **接通既有 `volume` 设置**：`AudioManager.setVolume(GameManager.instance.settings.volume)`；`MenuPage` 音量滑块改 `settings.volume` 后顺带调用 `setVolume`，**让现有滑块真正生效**（顺手修掉死设置）。
6. **接通既有 `item.sound` 数据**：在物品使用 Action（`ActionItem` 等）中读取 `item.sound`，映射到音效 ID（如 `'scroll'`→`sfx_scroll`），**激活已埋 3 年的死数据**。
7. **存档兼容**：`settings.volume` 已入 `SaveData`，无需改存档结构；音频资源本身不入存档。

> 接入顺序建议：先做 1→2→3（事件自动音效，零侵入、立竿见影），再做 4→5→6（点击反馈 + 修死设置/死数据）。

## 六、资源格式 / 压缩 / 包体影响

### 6.1 格式建议
| 用途 | 微信端 | 网页端 | 推荐编码 |
|------|--------|--------|----------|
| SFX 短音 | mp3（最稳） | mp3 / ogg | mp3 CBR 64–96kbps，**单声道** |
| BGM 循环 | mp3 | mp3 / ogg | mp3 96–128kbps，可立体声；ogg q4 更小 |
> 微信 `wx.createInnerAudioContext` 对 mp3 兼容最佳；ogg 在部分 Android 机型有兼容问题，**首版 SFX 一律 mp3**。

### 6.2 压缩要点
- SFX 转**单声道**（音效无需空间感），可再省 40–50% 体积。
- 短音效裁掉静音头尾，避免无效时长。
- BGM 循环点需做无缝处理（首尾淡入淡出或首尾采样对齐），否则循环处有"咔哒"。

### 6.3 包体影响评估
| 内容 | 估算体积 | 主包(4MB)占用 | 放置建议 |
|------|----------|---------------|----------|
| SFX 15–20 个（单声道 mp3） | 0.2–0.4MB | 5–10% | 主包 `audio/` 或**分包** |
| BGM 1–3 首（若首版做） | 0.3–2.0MB | 视情况 | **分包 / 远程 CDN** |
| 当前 JS 代码包 | 远小于 4MB | — | 主包 |
> 当前为纯代码文字游戏，主包大量富余。**强烈建议音频放进分包**（或 BGM 走 CDN），完全不挤占 4MB 主包，为后续美术/更多内容留余量。网页端无此限制。

## 七、后续路线图（P2+，若首版未做 BGM 或静音兜底）

- **P2 — 完整音频层**：接入 BGM（`bgm_ambient/dungeon/battle/boss`），战斗/地牢场景自动切换；音效分层混音；接通所有 `GameEvents` 自动音效。
- **P3 — 场景化音频**：城镇/森林/地牢不同环境 ambience；转生/阵营选择专属 sting；音效淡入淡出与随机变体（避免单调）。
- **P4 — 可选配音**：剧情事件关键节点轻量语音（需评估包体与本地化成本）。
- **静音首版兜底**（仅当首版确实不做音频时）：保留 `volume` 设置 UI 但标注"音频即将上线"；`AudioManager` 先以空实现（no-op）存在，保证接口稳定，P2 直接填充，业务层无需改动。

## 八、风险与开放问题

| 风险 | 等级 | 应对 |
|------|------|------|
| 微信首次播放需用户交互解锁 | 中 | `MainScene` 首次 touch 后 init/unlock |

| `item.sound` 死数据未映射 | 低 | §5.6 建立 id→音效映射表 |
| BGM 版权 | 低 | 用 CC0/自制，避免商用风险 |
