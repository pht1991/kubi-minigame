# 横屏桌面适配方案（B 方案）

> 目标：让游戏在**桌面浏览器**直接以横屏宽布局可玩（不需要微信开发者工具的 H5 预览模式），同时**手机/微信端保持原竖屏、零回归**。

## 一、诊断结论（为什么现在不适配）
- 设计分辨率锁死 `750×1334` 竖屏，`ResolutionPolicy.FIXED_WIDTH`。
- 桌面宽屏下：竖屏画布被等比缩成中间一根窄长条、两侧填 `#333` 深灰 → 视觉上"没适配手机屏"。
- **关键发现**：`750` 的硬编码几乎只在外壳层（`MainScene` 状态栏/底栏/网格 + `theme.ts` 常量 + `ModalPanel`）；16 个页面与弹窗（`ModalPanel` 已读 `view.getVisibleSize()` 自适应）全部用相对布局，**分辨率无关**。
- 因此 B 不是"重做 14 页"，而是**让外壳宽度感知 + 引入响应式分辨率**，整局自动重排。

## 二、核心改动（使能层，本次已落地）
1. **新增 `assets/scripts/ui/layoutConfig.ts`**：单一真相源 `Layout{ designW, designH, landscape }`。
2. **`MainScene.onLoad`**：按平台决定分辨率
   - 桌面浏览器（`sys.platform==='WEB' && !sys.isMobile`）→ `1280×720` 横屏；
   - 手机/微信/移动端浏览器 → 保持 `750×1334` 竖屏（分支走原值，**字节级不变**）。
3. **`MainScene` 外壳宽度感知**：状态栏 `SB_W`、底栏 `BAR_W`、网格 `VIEW_W` 改读 `Layout.designW`；状态栏 6 个属性在横屏下沿全宽均布（竖屏保留原 `-300~300` 写死位置）。
4. **`GridComponent.renderCells`**：横屏（`Layout.landscape && columns>1`）时按可用宽度推导列数（≤8）并让横条铺满，使主网格用满横屏宽度；竖屏保持原 `columns/barWidth` 不变。

## 三、为什么手机端零回归
- 所有横屏逻辑都由 `Layout.landscape` 守卫；竖屏分支直接走原有常量/位置。
- `setDesignResolutionSize` 在桌面/竖屏传入不同值，但竖屏分支传的就是原来的 `750/1334`。
- 安全区域计算（`_fetchSafeArea`）仅在 `typeof wx !== 'undefined'` 时运行（微信专属），桌面走不到。

## 四、剩余工作（Phase 2，需浏览器目测 + 逐页微调）
- **逐页视觉验收**：页面用相对布局，横屏下部分列表会变"宽而疏"。首版可接受；后续可对重点页（主页/背包/制造/地图）做 `maxWidth` 居中或两栏，提升横屏观感。
- **弹窗比例**：`ModalPanel` 默认 `panelW=640` 在横屏下显得偏窄，可让横屏时按比例放大（待验收后调）。
- **输入**：鼠标=触摸已可用；如需键盘快捷键（如 1/2/3 选底栏）为加分项，非必需。
- **网格列数上限**：当前封顶 8 列，超宽屏可放宽（验收后定）。

## 五、验证方式
- 编译：跑 `deploy-web.bat` 头less 构建（会触发 Cocos 编译，能抓 TS 错误），构建完自动推 gh-pages。
- 视觉：桌面浏览器打开 `https://pht1991.github.io/kubi-minigame/` 目测横屏布局；手机浏览器/微信应仍为竖屏。
- 回归：微信小游戏构建（`deploy-wechat.bat`）与手机端表现应与原版一致。

## 六、风险
- 桌面横屏的**视觉精细度**无法在本环境目测，需人工浏览器验收（首版可能需微调间距/字号）。
- 网格列数推导若某页 `tileW+spacing` 异常，可能出现列数=1 退化；已用 `Math.max(fit, columns)` 兜底保持原列数下限。
