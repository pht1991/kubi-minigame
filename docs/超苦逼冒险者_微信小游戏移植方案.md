### 1.4 技术特征与痛点

**核心依赖链**：`React 组件` → `jQuery DOM 操作` → `Babel 浏览器端编译` → `Bootstrap 样式`

| 特征 | 移植影响 |
|------|----------|
| React 老版本 + Context API | 状态管理逻辑可复用，但组件层需重写 |
| jQuery DOM 操作 | 小游戏无 DOM，需完全替换 |
| Babel 浏览器端编译 | 小游戏不支持，需预编译 |
| Cookie / localStorage 存档 | 需迁移至 wx.setStorageSync |
| 鼠标事件（hover/right-click） | 需适配为触摸事件 |
| Bootstrap CSS 布局 | 需用游戏引擎 UI 系统重建 |
| 音频播放 | 需迁移至 wx.createInnerAudioContext |

## 二、移植核心挑战

### 挑战 1：无 DOM 环境

微信小游戏**不是浏览器环境**，没有 `document`、`window`、`element` 等 DOM API。原游戏从 UI 渲染到事件绑定全部依赖 DOM，这是最大的迁移障碍。

### 挑战 2：React 组件重写

原游戏 30+ React 组件深度耦合 DOM。`React.render()` 直接操作 `document.body`，组件内大量使用 `refs`、`findDOMNode()` 等 DOM API。

### 挑战 3：交互模式适配

原游戏支持鼠标 hover（显示物品详情）、右键（装备/使用）、Ctrl/Shift 快捷键。小游戏只有触摸操作，需要重新设计交互。

### 挑战 4：包体大小限制

微信小游戏主包限制 **4MB**，总包（含分包）**20MB**。原项目 jQuery + React + Bootstrap 库本身就超 500KB，加上资源文件需要做瘦身。

### 挑战 5：存档系统迁移

原游戏使用 Cookie/localStorage 或后端 API 存档。小游戏需使用 `wx.setStorageSync`，且存档数据可能较大（建筑/物品/事件状态），需考虑序列化和容量。

## 三、三套方案对比

### 方案 A：Cocos Creator 重构（推荐）

**思路**：用 Cocos Creator 3.x 重建 UI 层，移植游戏逻辑层，数据层直接复用。

```
原项目分层                    Cocos Creator 新项目
┌─────────────┐              ┌─────────────────┐
│  React 组件  │  ──重写──→   │  Cocos UI 组件   │
│  (UI 层)     │              │  (Label/Button/  │
│  jQuery DOM  │              │   ScrollView)    │
├─────────────┤              ├─────────────────┤
│  main.js     │  ──移植──→   │  GameLogic.ts    │
│  (逻辑层)    │  去DOM化      │  (纯逻辑,无UI)   │
├─────────────┤              ├─────────────────┤
│  data_*.js   │  ──复用──→   │  data_*.ts       │
│  (数据层)    │  几乎不改     │  (直接搬运)      │
├─────────────┤              ├─────────────────┤
│  Cookie/API  │  ──替换──→   │  wx.Storage      │
│  (存档层)    │              │  + 云存储         │
└─────────────┘              └─────────────────┘
```

| 维度 | 评估 |
|------|------|
| 工作量 | 中高（UI 层全部重写，逻辑层去 DOM 化） |
| 技术风险 | 低（Cocos 对小游戏支持成熟） |
| 性能 | 优（原生 Canvas/WebGL 渲染） |
| 可维护性 | 优（TypeScript + 组件化） |
| 后续扩展 | 优（加广告/社交/排行榜方便） |
| 审核通过率 | 高（正规引擎开发） |

### 方案 B：原生 Canvas + 轻量 UI 框架

**思路**：不引入游戏引擎，直接用 `wx.createCanvas()` 绘制，自建文字 UI 框架。

| 维度 | 评估 |
|------|------|
| 工作量 | 高（需自建 UI 系统：文字排版/按钮/列表/弹窗） |
| 技术风险 | 中（文字排版在 Canvas 上比较麻烦） |
| 性能 | 优（最轻量） |
| 包体 | 最小（无引擎开销） |
| 可维护性 | 中（自建框架缺乏生态） |
| 后续扩展 | 差（加复杂功能需大量手写） |

### 方案 C：weapp-adapter 适配运行

**思路**：用微信官方 Adapter 模拟 DOM API，尽量直接跑原有 React 代码。

| 维度 | 评估 |
|------|------|
| 工作量 | 低中（主要改适配层） |
| 技术风险 | 高（Adapter 不完整，老 React 兼容性差） |
| 性能 | 差（DOM 模拟有开销，文字游戏尚可接受） |
| 包体 | 大（React + jQuery + Adapter） |
| 可维护性 | 差（黑盒适配，debug 困难） |
| 后续扩展 | 差（受限于适配层） |

### 方案 D：微信小程序（非小游戏）

**思路**：不做成"小游戏"而是"小程序"，用 WXML/WXSS 重建 UI，或用 web-view 嵌入 H5。

| 维度 | 评估 |
|------|------|
| 工作量 | 低（web-view 方案几乎零改动） |
| 技术风险 | 低 |
| 性能 | 中（web-view 有渲染开销） |
| 限制 | web-view 组件需要业务域名 + 配置，且无法使用小游戏专属 API（广告/排行榜） |
| 分发 | 走小程序分类，不在"游戏"入口，流量小 |

## 四、推荐方案：Cocos Creator 重构（方案 A）

### 4.1 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 游戏引擎 | Cocos Creator 3.8 LTS | 小游戏支持最成熟，UI 系统完善 |
| 语言 | TypeScript | 类型安全，IDE 支持好 |
| UI 系统 | Cocos UI（Label/Button/ScrollView/Layout） | 文字游戏最佳选择 |
| 存档 | wx.setStorageSync + 分包加载 | 本地为主，可选云存储 |
| 音频 | wx.createInnerAudioContext | 小游戏标准方案 |
| 状态管理 | 自建 EventTarget + 数据中心 | 替代 React Context |

### 4.2 架构设计

```
┌─────────────────────────────────────────────────┐
│                   Cocos Creator                  │
│                                                   │
│  ┌─────────────────────────────────────────┐     │
│  │            UI Layer (场景/预制体)          │     │
│  │  MainScene → 各功能面板预制体              │     │
│  │  (BagPanel/StatePanel/StudioPanel/...)   │     │
│  └────────────────┬────────────────────────┘     │
│                   │ 事件绑定                       │
│  ┌────────────────▼────────────────────────┐     │
│  │         GameLogic Layer (TS)             │     │
│  │  GameManager (状态中心)                    │     │
│  │  ├── SurvivalSystem (生存)                │     │
│  │  ├── CraftSystem (制造)                   │     │
│  │  ├── CombatSystem (战斗)                  │     │
│  │  ├── EventSystem (事件)                   │     │
│  │  ├── TradeSystem (贸易)                   │     │
│  │  ├── DungeonSystem (地牢)                 │     │
│  │  └── TimeSystem (时间)                    │     │
│  └────────────────┬────────────────────────┘     │
│                   │ 数据读写                       │
│  ┌────────────────▼────────────────────────┐     │
│  │          Data Layer (TS)                 │     │
│  │  data_item / data_event / data_mst / ... │     │
│  │  (从原项目 data_*.js 直接迁移)             │     │
│  └────────────────┬────────────────────────┘     │
│                   │                               │
│  ┌────────────────▼────────────────────────┐     │
│  │          Storage Layer                   │     │
│  │  SaveManager → wx.setStorageSync          │     │
│  │  AudioManager → wx.createInnerAudioContext│     │
│  └─────────────────────────────────────────┘     │
└─────────────────────────────────────────────────┘
```

### 4.3 迁移步骤

#### 第一阶段：项目搭建与数据迁移（1-2 周）

1. **创建 Cocos Creator 项目**
   - 选择 2D 模板，配置微信小游戏构建平台
   - 设置设计分辨率 750×1334（竖屏适配文字游戏）
   
2. **迁移数据层**
   - 将 `data_*.js` 转为 TypeScript，添加类型声明
   - 验证数据完整性（物品/建筑/配方/怪物等）
   - 这部分代码量最大但改动最小，是纯数据

3. **搭建核心框架**
   - `GameManager`：全局状态管理（替代 React Context）
   - `SaveManager`：存档读写（替代 Cookie/localStorage）
   - `EventBus`：事件系统（替代 React 状态更新触发重渲染）

#### 第二阶段：核心系统移植（2-3 周）

4. **移植生存系统**
   - 状态衰减逻辑（饥饿/水分/精神/体温）
   - 时间推进（日夜交替/季节循环）
   - 死亡判定与处理

5. **移植物品与制造系统**
   - 背包/箱子管理
   - 制造/烹饪/炼金/酿酒配方匹配
   - 装备穿戴与耐久度

6. **移植战斗系统**
   - 怪物属性计算
   - 技能加成公式
   - 冷却机制
   - 战斗流程（回合制）

7. **移植事件与任务系统**
   - 事件触发条件
   - 任务链状态机
   - 阵营选择
   - 转生系统

#### 第三阶段：UI 层重建（2-3 周）

8. **主界面布局**
   - 顶部：状态栏（6 维状态 + 时间/日期）
   - 中部：场景内容区（可滚动文字 + 按钮）
   - 底部：功能导航栏（背包/建造/技能/地图/菜单）

9. **功能面板实现**
   - 背包面板（物品列表 + 详情弹窗）
   - 制造面板（分类 Tab + 配方列表 + 批量制造）
   - 状态面板（数值 + 进度条 + 描述）
   - 战斗面板（怪物信息 + 技能选择 + 战斗日志）
   - 地图面板（地点列表 + 探索进度）
   - 贸易面板（商人列表 + 交易界面）
   - 地牢面板（楼层 + 事件 + 商人）

10. **交互优化**
    - 长按替代右键（装备/使用菜单）
    - 点击物品弹出详情面板替代 hover
    - 滑动手势切换面板
    - 批量操作按钮（制造数量选择）

#### 第四阶段：适配与优化（1-2 周）

11. **性能优化**
    - 文字渲染使用 Cocos Label（BatchRender）
    - 长列表使用 ScrollView + 模板复用
    - 减少节点数量，合并静态文字

12. **包体优化**
    - 精简 res/ 资源（压缩图片/音效）
    - 数据文件分包加载
    - 按需加载场景资源

13. **存档迁移**
    - 存档数据结构设计（JSON 格式）
    - 自动存档 + 手动存档
    - 存档版本管理（应对后续更新）

14. **小游戏适配**
    - 触摸事件适配
    - 分享功能（wx.shareAppMessage）
    - 录屏分享（wx.getGameRecorder）

#### 第五阶段：测试与上线（1-2 周）

15. **测试**
    - 功能测试（全系统流程跑通）
    - 兼容测试（iOS/Android/不同机型）
    - 性能测试（帧率/内存/包体）

16. **合规与审核**
    - 内容自查（文字内容合规）
    - 隐私政策配置
    - 提交审核

### 4.4 交互适配方案

| 原操作 | 小游戏适配方案 |
|--------|---------------|
| 鼠标 hover 看详情 | 点击物品 → 弹出详情面板 |
| 右键装备/使用 | 长按物品 → 弹出操作菜单 |
| Ctrl + 点击（批量） | 数量选择器 → 滑动选择数量 |
| Shift + 点击 | 暂不支持，改为菜单选项 |
| 键盘快捷键 | 底部快捷栏按钮 |
| 滚轮滚动 | 触摸滑动 |

### 4.5 存档数据结构

```typescript
interface SaveData {
  version: string;              // 存档版本
  playerState: {                // 玩家状态
    temp: number; full: number; moist: number;
    hp: number; ps: number; san: number;
  };
  currentEquip: Record<string, string>;  // 当前装备
  skill: Record<string, number>;         // 技能等级

  buildingSaveData: Record<string, any>; // 建筑数据
  durableSaveData: Record<string, number>; // 耐久度
  eventSaveData: Record<string, any>;    // 事件进度
  dungeonSaveData: Record<string, any>;  // 地牢数据
  campSaveData: string;                  // 阵营
  coolDownSaveData: Record<string, number>; // 冷却
  timeData: { day: number; hour: number; season: number };
  maouLevel: number;                     // 魔王轮回
  settings: { autoSave: boolean; volume: number; };
}
```

## 五、风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 数据层迁移遗漏 | 中 | 建立数据校验脚本，自动化比对 |
| 事件系统逻辑复杂 | 高 | 先画事件流程图，逐条迁移并测试 |
| UI 重写工作量大 | 中 | 优先实现核心面板，复用组件 |
| 包体超限 | 低 | 数据分包 + 资源压缩 |
| 审核不通过 | 低 | 文字内容自查，避免敏感词 |
| 老代码逻辑理解偏差 | 中 | 对照原游戏实机测试验证 |

## 七、后续可扩展方向

1. **云存档**：接入微信云开发，实现跨设备存档同步
2. **社交功能**：好友互助、资源赠送
3. **排行榜**：生存天数、轮回次数排行

_方案不替老板做决定，但推荐方案 A。理由：Cocos Creator 是小游戏生态最成熟的引擎，UI 系统天然适合文字游戏，后期加广告/排行榜/云存档都方便。方案 C（Adapter）看似省事但坑多，老 React + jQuery 的组合在 Adapter 上大概率跑不稳，debug 成本不可控。_
