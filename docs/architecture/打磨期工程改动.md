## 一、结论概览

经对 `assets/scripts/` 实际代码勘察，PROGRESS.md / 派工文档列出的 4 类缺陷中，**对象池、UI_REFRESH 节流、GridCell.onDestroy、battle 公式统一、hunt 扣减的「代码骨架」在现有代码库中多数已落地**（应为此前提交已修复）。

本次工程主管实际定位并修复的**真实残留缺陷**是：

- **缺陷 #2 真身（逻辑）**：交互式地图狩猎路径 `OutdoorPage → ActionMap.probeHunt + BattlePanel.startBattle`（走 `ActionCombat` 交互式战斗）**从不扣减 `mst.amount`**。`ActionMap.hunt()` 内部虽已实现扣减，但 **UI 从未调用 `hunt()`**（grep 确认仅有定义、无调用方），导致扣减逻辑是死代码——这就是「地图怪数量不递减」在真实玩家路径上的表现。

其余项均已在代码中确认到位，本次仅做**强化与清理**，并在本说明中逐项留存勘察结论，供架构/代码评审（full 门控）核对。

## 二、实际改动文件清单

| 文件 | 改动 | 类型 |
|------|------|------|
| `actions/ActionCombat.ts` | 新增「胜利一次性回调 `_onWin`」机制：`init(mstId, prefix?, onWin?)` 第三参数；`checkEnd` 胜利分支触发；`flee` 成功 / 死亡 / `clear` 全路径清空，防闭包泄漏与误触发 | 逻辑修复 |
| `ui/BattlePanel.ts` | `startBattle(mstId, prefix?, onWin?)` 透传 `onWin` 至 `ActionCombat.init` | 逻辑修复（透传） |
| `actions/ActionMap.ts` | 抽出公共方法 `consumeHuntedMonster(placeId, mstId)`（扣减 amount + 发 `place_change`），`hunt()` 复用；供交互式路径注入胜利回调；幂等（amount≤0 不继续递减） | 逻辑修复 |
| `ui/pages/OutdoorPage.ts` | 地图狩猎「交互式战斗」路径注入 `onWin` 回调：胜利时扣减该地点怪物数量 | 逻辑修复 |
| `ui/GridComponent.ts` | 将**页脚格子**纳入 `_cellPool` 对象池（原 `clearFooter` 每次 render 全量 `destroy`），并补齐复用节点时清除残留触摸监听（与正文格一致），彻底消除列表全量 `destroy`+`instantiate` | 性能强化 |
| `actions/ActionItem.ts` | 清理过时文件头注释（`使用（食物回状态）` → `使用（食物/状态道具/容量道具/技能书等）`） | 注释清理 |

### 改动要点说明

**1. 为什么用「胜利一次性回调」而不是覆写 `battlePanel.onEnd`？**
`DungeonPage` 既有模式是覆写 `battlePanel.onEnd`，并在房间结算后将其置 `null`。若 `OutdoorPage` 也覆写 `onEnd`，而 `MainScene.triggerBattle` 启动战斗时**不重置 `onEnd`**，则一次地图战后残留的 `onEnd` 闭包会在后续任意无关战斗（如主场景战斗网格）胜利时被误触发，错误扣减某地点怪物数量。
将扣减收敛进 `ActionCombat.init` 的 `onWin`（战斗内部状态机职责，胜利时触发一次、随即清空），与 `BattlePanel.onEnd`（UI 外层职责）**职责分离、互不影响**，从根上规避了闭包泄漏/误扣减。

**2. 页脚对象池复用安全性**
正文格与页脚格同为 `GridCell` 节点（均经 `createCellNode` 创建），布局在每次 render 时由 `setLayout/setData` 重设，故可安全共用同一 `_cellPool`。关键修复：复用节点在绑监听前 `node.off(TOUCH_START/END/CANCEL)` 清除上一轮残留监听（与 `renderCells` 做法对齐），否则 `onTouchEnd` 会叠加触发导致一次点击触发多次。

## 三、已确认到位、无需改动的项（代码勘察结论）

- **缺陷 #1 战斗解算一致性**：`ActionDungeon.battle()` 已通过 `ActionCombat.applyPrefix`（前缀修正）、`ActionCombat.calcPlayerAtk`、`ActionCombat.calcDamageReduce`（装备减伤）、`ActionCombat.decayWeapon / decayArmor`（耐久消耗）**复用同一套公式**。交互式 `ActionCombat` 与自动 `battle()` 的**解算数学一致**（前缀/减伤/耐久均已接入）。两者唯一差异是「自动循环解算 vs 交互式逐回合」，属表现层。
- **缺陷 #3 对象池 / UI_REFRESH 节流**：`GridComponent` 已有 `_cellPool`（正文格复用）与 `onUIRefresh` 内的 `scheduleOnce(..., 0.05)` 节流（合并高频 `UI_REFRESH`/`SKILL_CHANGE`/`EVENT_TRIGGER` 为一次 `renderPage`）。本次仅扩展覆盖页脚格。
- **缺陷 #4 GridCell.onDestroy**：`GridCell.onDestroy()` 已实现并调用 `cancelLongPressDetect()` 清理 `setTimeout`。确认有效，未改动。

## 八、D1 事件战斗交互式实现（Option A）

> 关联任务：T-ENG-D1 ｜ 优先级：P0 ｜ 角色：工程主管（程基岩）
> 决策依据：`打磨期设计裁决.md §1.2（推荐 Option A）`、`§5（工程实现注意点 · 时序陷阱）`
> 老板已拍板 D1=Option A（交互式战斗，最一致），故 §四「假设 A」原默认（“不改为交互式”）被推翻，按本节约落。

### 8.1 目标与口径

把事件中遇怪从「自动解算 `ActionDungeon.battle()`」统一为「交互式 `BattlePanel.startBattle`」，与地图狩猎（`OutdoorPage`）、地牢（`DungeonPage`）**完全同规则**：玩家可放技能、选防御/敏捷姿态、用道具、**能逃跑**。消除“同一只怪在地图可逃、在事件被强制无逃跑自动战”的后果层不公平。

- 事件奖励（`get` / `chanceGet` / `skill`）在触发时**先行结算**（现状已在 `onDone` 内先于战斗发放），战斗胜负**只影响玩家存亡**，不重复发奖励。
- 事件无「地点怪物 `amount`」概念，**不注入 `onWin` 扣减**（与 `OutdoorPage` 地图路径不同，无需递减）。

### 8.2 改动文件清单

| 文件 | 改动 | 类型 |
|------|------|------|
| `core/EventBus.ts` | 新增事件名 `EVENT_BATTLE_REQUEST: 'event_battle_request'`（事件系统段） | 信号新增 |
| `actions/ActionEvent.ts` | `trigger` 的 `onDone` 内：遇 `data.mst` 时由 `this._dungeon.battle(data.mst)` 改为 `this._eventBus.emit(GameEvents.EVENT_BATTLE_REQUEST, data.mst)`；删除已无用的 `ActionDungeon` 依赖（import / `_dungeon` 字段 / 构造赋值） | 逻辑改造 |
| `ui/pages/EventPage.ts` | 新增构造订阅 `EVENT_BATTLE_REQUEST` → `openEventBattle(mstId)`：设置 `battlePanel.onEnd = () => eventBus.emit(UI_REFRESH)`，再 `battlePanel.startBattle(mstId)`（与地牢/地图同规则，事件无需 `onWin`） | 逻辑改造（UI 接力） |

### 8.3 时序如何处理（重点 · 时序陷阱）

`ActionEvent.trigger` 走 `ActionExecutor.execute(..., 0.1, { onDone })`，其中 `timeNeed=0.1` 经 `ProgressOverlay` 异步结束后才执行 `apply()` → `options.onDone()`。

`onDone` 内部**严格顺序**为：

1. 发事件奖励（`get` / `chanceGet` / `skill`）；
2. 标记 `experienced = true` 并发 `EVENT_TRIGGER` / `ITEM_CHANGE`；
3. 若 `data.mst`：`emit(EVENT_BATTLE_REQUEST, data.mst)`。

第 3 步的 `emit` 是**同步**派发，`EventPage` 的订阅处理器当场被调用，当场执行 `battlePanel.startBattle(mstId)`（`ActionCombat.init` 同步建状态 + 面板置 `active`）。因此：

- **奖励先落档、再开战**：奖励结算（步骤 1-2）与开战（步骤 3）处于同一个同步 `onDone` 调用栈内，没有任何 `await`/定时器插入其间，**奖励必然先于战斗写入内存状态**，不存在“战斗先开、奖励未落档”的间隙。
- **存档原子性不被破坏**：`onDone` 内所有对 `GameManager` 的改动（奖励、标记、开战后的 HP/耐久/掉落）都在同一同步栈完成；`ActionExecutor` 在 `onDone` 之后才 `emit(UI_REFRESH)`（仅刷新 UI，不含存档写盘），而真正落盘由 `setMsg`/自动存档在栈外发生。拆分前后逻辑等价——原 `battle()` 也是在同一 `onDone` 内同步跑完，拆分“发信号 + UI 接 startBattle”只是把解算入口从 `ActionDungeon.battle` 换成了 `ActionCombat.init`，**没有引入额外异步边界**。
- **`onEnd` 不二发奖励**：`EventPage.openEventBattle` 把 `battlePanel.onEnd` 设为「仅 `emit(UI_REFRESH)`」。战斗结束（`BattlePanel.close`）只刷新 UI，不触碰事件奖励；怪物自身掉落（`mst.reward`/`chanceGet`）仍由 `ActionCombat.checkEnd` 在胜利时正常发放（与旧 `battle()` 行为一致，属“击败怪物得战利品”，非事件奖励，不重复）。

### 8.4 公式零改动确认

底层统一公式**全部复用，未重写、未复制**：

- `ActionCombat.applyPrefix` / `calcPlayerAtk` / `calcDamageReduce` / `decayWeapon` / `decayArmor` —— 交互式面板经 `ActionCombat.init` 调用，与旧 `ActionDungeon.battle()` 同一套函数（见裁决 §0.1）。
- 战斗胜负、玩家 HP 失血、耐久消耗、装备减伤、前缀修正等数学完全一致；差异仅为“自动循环解算 vs 交互式逐回合”，属表现/玩家抉择层，符合裁决“同怪同规则，差异只允许来自玩家抉择”的口径。
- `ActionDungeon.battle()` 作为自动解算版仍保留（被其它调用方/潜在回退使用），本次仅**不再被事件路径调用**。

### 8.5 设计裁决未覆盖的细节与处理假设

1. **战斗来源上下文（裁决 §5.3）**：裁决称“若需经 `MainScene.onBattleEnd` 携带战斗来源（事件 vs 地牢 vs 地图）可补传上下文”，标的是 **D2 地图递减**（需 `placeId+mstId`）。本事件战斗**无来源特定后处理**（无递减、无房间结算），故**未引入来源上下文 plumbing**，仅设 `onEnd = UI_REFRESH`。既满足需求，也不破坏现有地牢/地图路径。若后续要为统计/埋点统一来源，可在 `EVENT_BATTLE_REQUEST` 载荷加 `source:'event'`，但本次不做以免碰现有路径。
2. **`onWin` 一次性回调**：T-ENG-01 已建机制（`ActionCombat.init` 第三参数）。事件无 `amount` 概念，无需扣减，**未注入 `onWin`**；职责清晰（`onWin` 留给 `OutdoorPage` 地图递减专用）。
3. **`data.mst` 形态**：经 `data_event.ts` 核实，事件 `mst` 为怪物 ID 字符串（如 `darkSoul`），**无前缀**；故 `startBattle(mstId)` 不传 `prefix`，与旧 `battle(data.mst, undefined)` 等价。
4. **d_2 后续对话与战斗叠加**：`doEventTrigger` 在 `trigger` 返回后同步弹 `d_2` 后续对话；战斗于 ~0.1h（≥350ms）进度后才开。故 d_2 对话先出现，战斗面板随后覆盖其上；战斗结束后 d_2 仍在底层，玩家点「继续」即可。功能正确，仅存在轻微 UI 层叠，非阻断项，标注为已知体验项（见回归项 4）。

### 8.6 待回归项（QA / 门控输入）

1. **事件战斗可逃/可选**：抽含 `mst` 的事件（如 `data_event.ts` 的 `darkSoul` 墓穴事件）触发，确认进入交互式面板，玩家可放技能/防御·敏捷/道具/逃跑；逃跑后存活、事件奖励已落档。
2. **奖励不重复发**：确认事件 `get`/`chanceGet`/`skill` 仅在触发时发一次；战斗胜利时仅得怪物 `mst.reward`，不再二次发事件奖励。
3. **阵亡走死亡流程**：事件战斗中 HP 归零应走 `ActionCombat.checkEnd` 的玩家死亡处理（`player_death`/转生重生），不再是无逃生必死陷阱。
4. **d_2 对话与战斗 UI 层叠**：确认含 mst 事件触发后 d_2 与战斗面板先后顺序/可关闭，无明显卡死（体验项，可接受）。
5. **公式一致性**：同怪同属性下，事件战斗与地图/地牢战斗伤害/减伤/耐久消耗一致（对照裁决 D4）。
6. **平衡回归**：Option A 交互式通常“更易”（有逃跑/防御），事件整体难度或下降，建议抽 3-5 个含 `mst` 事件做难度对照（对照裁决 §1.2 平衡风险）。
7. **无编译回归**：本地无 Cocos 编辑器，未跑全量编译；`node_modules/cc` 缺失的约 170+ tsc 假错为存量噪音，本次未触碰相关报错，改动仅为真实逻辑（信号新增 + 一处 emit 替换 + UI 订阅接力）。
